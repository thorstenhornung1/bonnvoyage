## 1. Test-Stack

### 1.1 Kernkomponenten

| Werkzeug | Zweck | Anmerkung |
|---|---|---|
| `pytest` | Test-Runner | mit `-p no:cacheprovider` in CI |
| `pytest-homeassistant-custom-component` (PHCC) | HA-Test-Harness (`hass`-Fixture, `MockConfigEntry`, `async_fire_time_changed`, `load_fixture`) | Version ist **an die HA-Version gekoppelt** → Matrix-Strategie, siehe §4.4 |
| `syrupy` | Snapshot-Tests für Entity-States, Registry-Einträge, Diagnostics | mit `HomeAssistantSnapshotExtension` aus PHCC; `.ambr`-Dateien werden committet |
| `aioresponses` | HTTP-Mocking auf `aiohttp`-Ebene für die API-Clients in `api/` | **eine** Mock-Bibliothek, nicht zusätzlich `respx` (respx mockt `httpx`, das wir nicht nutzen — Entscheidung dokumentieren) |
| `freezegun` (`freezer`-Fixture) | Zeitsteuerung für Trend-Logik, Intervalle, Backoff | Pflicht für alle zeitabhängigen Tests |
| `pytest-cov` / `coverage` | Coverage inkl. **Branch-Coverage** (`--cov-branch`) | Gates siehe §2 |
| `pytest-socket` (via PHCC aktiv) | **Blockiert echte Netzwerkzugriffe in Unit-Tests** | Live-Zugriffe nur im Contract-Marker erlaubt, siehe §5.3 |
| `pytest-timeout` | Hänger-Schutz (`--timeout=30`) | verhindert CI-Deadlocks bei Event-Loop-Fehlern |

Auf zwei Ebenen testen:

1. **API-Clients (`api/`) isoliert** — reine `aiohttp`-Clients ohne HA-Import, getestet mit `aioresponses` gegen Fixture-Payloads. Das ist die Voraussetzung für die spätere PyPI-Auslagerung (Platinum).
2. **Integration im HA-Kontext** — Config-/Subentry-/Options-Flows, Koordinatoren, Entities mit `hass`-Fixture; API-Clients hier per `patch`/`AsyncMock` an der Integrationsgrenze gemockt.

### 1.2 Fixture-Korpus (echte API-Antworten)

Verzeichnis `tests/fixtures/`, **einmalig von den Live-Endpunkten gezogen und eingefroren**; jede Datei mit Header-Kommentar (Quelle-URL, Abrufdatum). Pflichtvarianten je Quelle:

```
tests/fixtures/
├── bcp/
│   ├── bcpext_ok.xml               # Normalfall, alle Parkhäuser
│   ├── bcpext_empty.xml            # gültiges XML, 0 Parkhäuser
│   ├── bcpext_malformed.xml        # abgeschnittenes/kaputtes XML
│   ├── bcpext_not_xml.html         # Wartungsseite/HTML statt XML
│   ├── bcpext_missing_fields.xml   # Parkhaus ohne frei/kapazität/status
│   ├── bcpext_zero_capacity.xml    # Kapazität 0 → Division-by-Zero-Guard
│   ├── bcpext_closed.xml           # Parkhaus geschlossen
│   ├── bcpext_encoding.xml         # Umlaute/Encoding (ISO-8859-1 vs UTF-8!)
│   └── bcpext_oversized.xml        # übergroß (≥ 5 MB) → Größen-Guard
├── bonn_geo/
│   ├── baustellen_ok.geojson
│   ├── baustellen_empty.geojson    # leere FeatureCollection
│   ├── baustellen_invalid_geometry.geojson
│   ├── baustellen_missing_props.geojson
│   └── baustellen_error.html
├── autobahn/
│   ├── a565_warnings_ok.json / a565_roadworks_ok.json (analog A59, A555)
│   ├── warnings_empty.json
│   ├── warnings_malformed.json
│   └── error_5xx.html
└── routing/
    ├── tomtom_route_ok.json
    ├── tomtom_route_no_route.json  # kein Routenergebnis
    ├── tomtom_invalid_key.json     # 403-Body
    ├── tomtom_ratelimit.json       # 429-Body
    └── tomtom_malformed.json
```

Regeln:

- Fixtures sind **die einzige Quelle der Wahrheit** für Parser-Tests — keine handgeschriebenen Minimal-Payloads für den Happy Path.
- Kaputte Varianten dürfen synthetisch aus den echten abgeleitet werden (dokumentiert im Datei-Header).
- Personen-/schlüsselbezogene Daten (API-Keys in URLs) vor dem Commit entfernen.
- Fixture-Aktualisierung nur über den Contract-Test-Prozess (§5.3), nie ad hoc.

## 2. Coverage-Ziele & Durchsetzung

### 2.1 Ziele je Modul

| Modul | Ziel | Begründung |
|---|---|---|
| `config_flow.py` (inkl. **aller** Subentry-, Options-, Reauth-, Reconfigure-Schritte) | **100 %** (Statements **und** Branches) | Quality-Scale-Regel `config-flow-test-coverage` — bereits **Bronze**-Pflicht, nicht erst Platinum |
| `api/*` | **≥ 95 %** | Parser sind die fehleranfälligste Schicht; erlaubte Lücken nur `if TYPE_CHECKING`/`__repr__` |
| `coordinator.py`, `sensor.py`, `binary_sensor.py`, `geo_location.py`, `event.py`, `__init__.py` | **≥ 90 %** | |
| `diagnostics.py`, `repairs.py`, `system_health.py` | **≥ 90 %** | Redaction ist sicherheitsrelevant → Redaction-Pfade 100 % |
| Gesamt | **≥ 92 %** | globales Sicherheitsnetz |

### 2.2 Durchsetzung in CI

`coverage` kennt keine nativen Per-Modul-Schwellen — daher zweistufig:

1. **Global Gate** in `pyproject.toml`:

   ```toml
   [tool.coverage.run]
   source = ["custom_components/bonnvoyage"]
   branch = true

   [tool.coverage.report]
   fail_under = 92
   show_missing = true
   ```

2. **Per-Modul-Gate** über `coverage json` + Prüfskript `scripts/check_coverage.py` (stdlib-only), das `coverage.json` gegen eine Schwellen-Map prüft und mit Exit-Code ≠ 0 abbricht:

   ```python
   THRESHOLDS = {
       "config_flow.py": 100.0,
       "api/": 95.0,
       "": 90.0,  # Default für alle übrigen Module
   }
   ```

   CI-Schritt: `pytest --cov --cov-branch --cov-report=json && python scripts/check_coverage.py`.

Zusatzregeln:

- `# pragma: no cover` nur mit Begründungskommentar in derselben Zeile; wird im Review gezählt (Ziel: < 5 Stellen im Projekt).
- Coverage-HTML-Report als CI-Artefakt hochladen (Debugging von Lücken ohne lokalen Lauf).
- Optional (SOLL): `diff-cover` — neue/geänderte Zeilen im PR müssen 100 % abgedeckt sein; verhindert schleichende Erosion trotz erfüllter Gesamtquote.

## 4. CI-Pipeline (GitHub Actions)

### 4.1 `ci.yaml` — bei Push & PR

```
jobs:
  lint:        ruff check + ruff format --check
  typing:      mypy --strict custom_components/bonnvoyage
  hassfest:    home-assistant/actions/hassfest@master
  hacs:        hacs/action@main (category: integration)
  test:        Matrix, siehe 4.4 → pytest --cov --cov-branch --cov-report=json
               + python scripts/check_coverage.py
               + Upload coverage-HTML als Artefakt
```

- Alle fünf Jobs sind **Required Checks** für Merge auf `main` (Branch Protection).
- `concurrency: cancel-in-progress` je Branch; Dependency-Caching via `uv` (schnell, lockfile-basiert).
- PHCC deaktiviert Sockets → jeder versehentliche Live-Call schlägt im CI fehl (gewollt).

### 4.2 `nightly.yaml` — Contract-Tests (nicht blockierend)

- `schedule: cron "0 4 * * *"`, zusätzlich `workflow_dispatch`.
- Läuft **nur** `pytest -m contract` mit erlaubten Sockets gegen die Live-Endpunkte (BCP-XML, GeoJSON, Autobahn-API; Routing nur mit Secret-Key, sonst skip).
- Prüft **Schema, nicht Werte**: Pflichtfelder vorhanden, Typen korrekt, Encoding, HTTP 200, Antwortgröße plausibel.
- Fehlschlag ⇒ **öffnet/aktualisiert automatisch ein GitHub-Issue** (`actions/github-script`), blockiert aber keine PRs. Zusätzlich Job gegen `homeassistant==dev`/PHCC-Prerelease als Frühwarnung für kommende HA-Breaking-Changes (ebenfalls non-blocking).

### 4.3 `release.yaml`

1. Trigger: Git-Tag `v*`.
2. Guard: `manifest.json`-`version` == Tag (sonst Abbruch).
3. Voller CI-Lauf (lint/typing/hassfest/hacs/test) muss grün sein.
4. ZIP `bonnvoyage.zip` aus `custom_components/bonnvoyage/` bauen (HACS-`zip_release`-kompatibel).
5. GitHub-Release mit generierten Notes + ZIP-Asset; Changelog-Abschnitt aus `CHANGELOG.md` (Keep-a-Changelog-Format) erzwingen.

### 4.4 HA-Versions-Matrix

PHCC-Versionen sind an HA-Releases gekoppelt. Strategie:

- `requirements_test.txt` pinnt je Matrix-Zeile: **aktuelle HA** (heute: 2026.8.x) und **vorherige** (2026.7.x) mit jeweils passender PHCC-Version.
- Python-Version je HA-Vorgabe (aktuell 3.13).
- Monatlicher Chore-PR (Renovate/Dependabot oder Kalender-Reminder) hebt die Matrix nach jedem HA-Release an; der `dev`-Nightly-Job (§4.2) hat Inkompatibilitäten idealerweise schon vorher gemeldet.

## 5. Definition of Done & Regressionsstrategie

### 5.1 DoD je Milestone

**Für jeden Milestone gilt zusätzlich zur Feature-Liste:**

- Alle Testfälle des Katalogs (§3) implementiert und grün; Coverage-Gates (§2) erfüllt.
- `ruff`, `mypy --strict`, hassfest, HACS-Action grün. **mypy strict gilt ab M1**, nicht erst M4 — nachträgliches Typisieren ist der teuerste Weg.
- Keine neuen `# pragma: no cover` / `# type: ignore` ohne Begründung.
- Snapshots reviewed und committet; Fixtures für alle neuen Endpunkte inkl. Fehler-Varianten vorhanden.
- Doku (README-Abschnitt) für neue Features aktualisiert; `strings.json` + `translations/de|en` vollständig.

**Milestone-spezifisch:**

| Milestone | Zusätzliche DoD |
|---|---|
| **M1** | Test-Infrastruktur steht komplett (conftest, Fixture-Korpus BCP, CI-Pipeline §4.1 aktiv, Coverage-Gates scharf); Trend-Spezifikation dokumentiert und getestet; Basis-Flow + Parkhaus-Subentry 100 % Coverage |
| **M2** | geo_location-Lebenszyklus (erscheinen/verschwinden) unter Zeitsteuerung getestet; Event-Dedup nachgewiesen; Attribut-Größenlimits getestet |
| **M3** | Reauth-Flow 100 % Coverage; Provider-Interface-Testsuite läuft gegen alle Implementierungen; Key-Leak-Test (Logs) grün; Nightly-Contract-Job für Routing (mit Secret) aktiv |
| **M4** | Alle Platinum-Nachweise (§3.4) grün; `quality_scale.yaml` vollständig; Release-Workflow einmal end-to-end mit `v0.x`-Tag verifiziert; Diagnostics-Redaction-Test grün |

### 5.2 Snapshot-Regressionsprozess

- Snapshots (`.ambr`) sind Code: Änderungen erscheinen im PR-Diff und werden **inhaltlich reviewed** — ein Snapshot-Update ohne erklärende PR-Beschreibung ist ein Reject-Grund.
- Update ausschließlich via `pytest --snapshot-update` lokal, nie in CI.
- Faustregel: geänderter Snapshot ⇒ entweder beabsichtigtes Feature (im Changelog) oder Bug — nichts dazwischen.

### 5.3 Contract-Tests & Fixture-Refresh

- Nightly-Contract-Tests (§4.2) sind das Frühwarnsystem für API-Drift (BCP ändert XML-Schema, Bonn ändert GeoJSON-Properties, Autobahn-API-Versionierung).
- Prozess bei Drift: Issue aus Nightly → neue Live-Antwort als Fixture einfrieren (Datum im Header) → Parser + Unit-Tests anpassen → alte Fixture behalten, falls Übergangsphase (Parser muss ggf. beide Formen können) → Release.
- Contract-Tests sind bewusst **nie** Merge-Blocker: Flakiness externer APIs darf die Entwicklung nicht anhalten.

## 6. Was der Plan aus QA-Sicht ergänzen MUSS / SOLL / KANN

### MUSS (blockierend für Platinum bzw. für sinnvolles Testen)

1. **Teststrategie in die Roadmap ziehen: Test-Infrastruktur ist M1-Deliverable, nicht M4.** PLAN.md §8 nennt „100 % Flow-Coverage" erst in M4 — zu spät: `config-flow-test-coverage` ist bereits **Bronze**-Regel. CI, Coverage-Gates und Fixture-Korpus müssen mit dem ersten Feature-Commit stehen.
2. **`tests/`-Struktur + Fixture-Korpus als eigenes Arbeitspaket** in M1 aufnehmen (inkl. der kaputten/leeren/übergroßen Varianten aus §1.2 — insbesondere **Encoding-Fixture für BCP-XML**, Umlaute in Parkhausnamen sind ein realistischer Bruchpunkt).
3. **Trend-Logik spezifizieren, bevor sie implementiert wird** (offene Frage 3 im Plan): Fensterbreite, Hysterese, Verhalten nach Neustart und bei Datenlücken. Ohne Spezifikation sind M1-T1…T5 nicht abnehmbar — das ist aktuell die größte Testlücke im Plan.
4. **Fehler-Taxonomie der API-Clients definieren** (eigene Exception-Hierarchie je Client: `…ConnectionError`, `…ParseError`, `RoutingAuthError`, `RoutingRateLimitError`): Koordinator-Mapping (→ `UpdateFailed` vs. `ConfigEntryAuthFailed`) ist sonst nicht testbar.
5. **Reauth-Flow für den Routing-Key explizit als M3-Deliverable** mit 100 %-Coverage-Anspruch nennen (Silver-Regel `reauthentication-flow`; im Plan nur in der Checkliste erwähnt, nicht in der Roadmap).
6. **`mypy --strict` + `ruff` ab M1** im CI verankern (Plan verortet Typing in M4 — Nachrüsten über 4 Milestones ist der teuerste Weg).
7. **Per-Modul-Coverage-Durchsetzung** (Skript §2.2) — die Ziele „Flow 100 %, api ≥ 95 %" sind sonst nicht maschinell prüfbar.
8. **Keine Live-API-Zugriffe in Unit-Tests** (pytest-socket aktiv lassen); Live nur im Nightly-Contract-Job.
9. **Unavailability-Verhalten als Spezifikation** in den Plan: welcher Quellen-Ausfall macht welche Entities `unavailable` (Quellen-Isolation, M2-A6/M3-E5) — derzeit nur implizit in §3.4 des Plans.
10. **Versions-Matrix-Politik** dokumentieren: aktuelle + vorherige HA-Version, PHCC-Kopplung, monatlicher Bump (§4.4).

### SOLL (stark empfohlen)

1. Syrupy-Snapshots für **alle** Entity-Plattformen + Registry + Diagnostics als Standard-Testmuster (statt einzelner `state`-Asserts).
2. Nightly-Contract-Tests mit automatischer Issue-Erstellung (§4.2) inkl. `homeassistant==dev`-Frühwarn-Job.
3. `diff-cover` als PR-Gate (100 % auf geänderten Zeilen).
4. Übersetzungs-Paritätstest de/en (`test_translations.py`) — Gold-Anforderung, billig automatisierbar.
5. Log-Hygiene-Tests: Key-Leak-Test (M3-A6) und „nur ein Log pro Ausfallphase" (Silver-Regel zum Log-Spam).
6. Attribut-Größen-Guard testen (Recorder-Limit ~16 kB; Meldungsliste kappen, M2-V1).
7. Release-Dry-Run in M4-DoD (Tag → ZIP → HACS-Install manuell verifiziert).

### KANN (nice to have)

1. Property-based Testing (`hypothesis`) für XML-/GeoJSON-Parser (zufällig mutierte Payloads).
2. Mutation-Testing (`mutmut`) gezielt für Trend- und Enum-Schwellen-Logik.
3. Coverage-Badge + Codecov-Kommentare im PR.
4. Performance-Smoke-Test: Parse-Zeit `bcpext_oversized.xml` < 1 s (Schutz des Event-Loops).
5. Lasttest der Koordinator-Isolation mit `aioresponses`-Latenz-Simulation.
